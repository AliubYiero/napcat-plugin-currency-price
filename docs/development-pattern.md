# NapCat 插件开发范式总纲

本文是 NapCat 插件开发的通用范式总纲, 定义统一文档骨架、强度分级、生命周期铁律、分层架构模型, 并索引各专项范式。它不绑定任何具体业务——各专项文档正文零项目引用, 仅在末尾"参考实现"一节给出实例索引。

## 规范强度分级

本文档体系使用三档强度词, 在总纲定义一次, 各专项范式直接复用:

| 档位 | 语义 | 违反后果 |
| --- | --- | --- |
| **必须** | 结构性约束, 违反会引入崩溃/越权/数据损坏等实际缺陷 | 不允许违反; checklist 逐条核查 |
| **应该** | 强烈推荐的最佳实践, 偏离需有明确理由 | 允许偏离, 但偏离点应在代码注释或文档中说明 |
| **应该** 之外的弹性实践 | 在多种合理方案中选定一种, 保证项目内一致即可 | 项目内保持一致即可 |

> 各专项文档的"标准范式清单"中, 每条前标注其档位。

## 生命周期铁律

NapCat 插件加载流程: **模块 import → `plugin_init(ctx)` → 运行**。所有范式共同的前提由此而来:

1. 【必须】模块加载期 (import 时) `ctx` 尚未初始化。任何模块在加载期不得触碰 `ctx`、`ctx.dataPath`、`ctx.logger`, 不得做文件 IO, 不得调用发送函数。
2. 【必须】单例可以模块加载期导出, 前提是构造期零 IO (构造不读 ctx、不读文件、不读配置)。真正的 IO 全部推迟到 `plugin_init` 之后。
3. 【必须】全局状态经由唯一的全局状态单例访问 (含 config 读写与清洗、data 目录 JSON 持久化、logger、定时器注册表), 各模块不自行持有 ctx 或逐层传参。

各专项范式是这条铁律的具体化: store 的"延迟实例化" ([store-pattern](./store-pattern.md))、配置读写的"运行期才读盘" ([config-pattern](./config-pattern.md))、发送工具的"运行期才调用" ([message-send-pattern](./message-send-pattern.md))。

## 分层架构模型

```
入口 (index.ts)          生命周期装配, 不含业务
  → 接收层 (handlers)    消息过滤、前缀检查、指令分发   [instruction-pattern]
  → 执行层 (handlers)    按模块分目录的指令 handler
  → 业务层 (services)    轮询、解析、推送、上限等业务逻辑
  → 持久化层 (store)     JSON 文件读写, 单例 + 延迟实例化 [store-pattern]
  → 外部 API 层 (api)    上游服务 HTTP 封装, 与业务解耦
横切: 发送工具 [message-send-pattern]、配置 [config-pattern]、
      帮助输出 [help-output-pattern]、权限推导 [permission-pattern]
```

各层通用纪律:

- 【必须】**每层只做自己的事**: 接收层不认识指令语义, 分发层不做业务, handler 内不重复权限校验, store 不含业务规则。
- 【应该】**纯函数优先**: 解析、清洗、模板渲染等无 IO 逻辑抽为纯函数模块 (输入 → 输出, 不触碰 ctx / store), 便于独立理解与复用。
- 【必须】**外部 API 层与业务解耦**: HTTP 封装只做请求/响应与登录态注入, 不做业务判断; 业务层不直接拼 URL。
- 【应该】**失败回退链**: 可视化产物 (渲染图片等) 优先, 失败回退纯文本; 外部依赖不可用时降级而不崩溃。

## 领域建模纪律

- 【必须】领域术语以 `CONTEXT.md` 为唯一权威: 新术语在概念定型时即写入, 带 _Avoid_ 项; 与代码冲突时先校对再改。
- 【应该】默认值语义 (尤其是启用开关的默认开启/关闭) 属于领域决策, 在 `CONTEXT.md` 声明, 必要时补 ADR。
- 【应该】状态机类概念 (如"直播会话""订阅会话") 明确事件何时有意义、基线何时重置。

## 架构决策记录 (ADR) 纪律

当一项决策同时满足以下三条判据时, 应该写一份 ADR:

1. **难逆转**: 一旦实现铺开, 改回来要动多处代码或迁移数据。
2. **无上下文会意外**: 半年后看到这段代码, 不读决策记录会想不通"为什么这样做"。
3. **真实权衡**: 存在被放弃的合理方案, 放弃理由值得留存。

ADR 为单文件 Markdown, 置于 `docs/adr/` 目录, 命名 `NNNN-kebab-case-标题.md`, 正文包含: 背景与问题 → 被放弃的方案与理由 → 结论 → 该决策约束的范式文档。被新决策推翻的旧 ADR 保留文件并标注状态, 不删除。

## 指南的生长

以下区域已有参考实现但暂无专项范式。新增同类代码前先确认该区域是否已有现成实现可提炼; 提炼成文时按上文六段骨架新建 `*-pattern.md` 并登记到 [index.md](./index.md):

- **API 请求层**: 外部服务 HTTP 封装的职责划分与错误处理。
- **services 业务纪律**: 轮询 (定时器 + 增量比对)、纯函数解析、推送 (渲染 + 回退)、上限控制。
- **插件入口装配**: 生命周期函数的注册与初始化顺序。

尚未成文的区域, 参照现有实现; 提炼出新范式文档后, 上述清单相应缩短。

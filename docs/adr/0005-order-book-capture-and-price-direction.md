# 0005 - 采集盘口数据，并且价格一律按「个/元」方向存储

> **与另两条同批落地**：本文件记录的是「采集盘口 + 双向存储」这个决定本身。价格**取自哪里**见 [ADR-0006](./0006-api-response-as-price-source.md)，价格**什么时候不算数**见 [ADR-0007](./0007-thin-market-means-distorted.md)。

## 背景与问题

设计文档 §2「非目标」写着：**不做价格趋势分析 / 图表，不做历史价格查询**。本次却要在每个通货上增加「获取详情」——点进挂单面板，采集**成交量**与**前 N 条挂单**（库存量 + 比率价），并出现在 `price` 消息与定时推送里。

这与原设计取向（抓取面最小）是冲突的：成交量和盘口厚度正是价格趋势分析的原料，而这份数据一存在，"按成交量排序""看盘口厚度"这类追问几乎是必然的。

同时，实现过程中发现站点对同一个价格**显示两个方向**：

- 第一行 `1 <通货> = <值> 元` → `元/个`（每个值多少元）
- 第二行 `1 元 = <值> <通货>` → `个/元`（每元能买几个）

两个方向精度不同。`1 元 = 3800 个` 用 `元/个` 表示是 `0.0003`，而页面只显示 4 位小数——那个方向在空间上够、在数值上不够。

**关键事实：两行不是互逆的。** 它们各按自己的小数位独立显示。实测同一时刻页面上 `1 个 = 0.003 元` 与 `1 元 = 314.3911 个` 并存，而 `1/0.003 = 333.333`——**差 6%**。详情接口同理：`ratioPrice: 160.006` 与 `rmbPrice: 0.0063` 是两个独立字段，不是彼此的倒数。

## Considered Options

**不采集盘口，维持非目标（已否决）**。最省事，且不与文档冲突。否决理由：用户的实际需求是判断"这个价好不好卖"，而单看价格给不出答案——成交量与挂单厚度才是。文档的非目标针对的是「趋势图表与历史查询」这类**展示与分析**形态，采集原料并不等于要做那些。

**只存一个方向、另一个用取倒数算出来（已否决）**。看起来能省一半字段，实际会产出**在页面上找不到的数**：`0.003` 的倒数是 `333.333`，而页面写的是 `314.3911`。这个错值看起来完全合理，且与真实值的差距只有 6%——肉眼看不出，事后也难以发现。**这是本次实现中真实踩过的坑**（一个通货的 `price` 被算成了 `0.003` 的倒数方向）。

**两个方向都存（已采纳）**。曾经的否决理由是"同一事实的两份拷贝，会失步"——那个理由建立在一个**错误的前提**上（以为两行互逆）。既然两行是**两个独立的事实**（页面自己给的两组数），存两份就不是冗余，而是把页面已有的信息如实带下来。

**详情失败判游戏失败（已否决）**。现有硬约束是「任一区服组合失败 → 整个游戏本轮作废」。但详情的失败面比价格大得多（一次点击 + 一次接口等待），而它**不产生错值**——"没去取"与"取不到"在数据里是可区分的。让一个冷门通货的详情超时把整份价格赔进去，收益为零。

## 结论

**1. 采集盘口数据，但仍不做趋势分析与历史查询**。本次只做"抓下来 + 显示在消息里"，§2 的非目标措辞相应收窄为「不做价格趋势分析 / 图表 / 历史价格查询指令」。

**2. 两个方向都抓、都存、都展示，任何地方都不许用取倒数换算。**

- 价格记录带**主方向**（`price` / `unit`）与 **`rmbPrice` / `rmbUnit`** 两对字段。⚠️ 初稿把后者叫 `reversePrice` / `reverseUnit`，**该命名已废弃**——`reverse*` 是**相对命名**（"相对于主方向"），主方向一改它就得跟着改；`rmb*` 是**绝对命名**，与站点、与抓取源项目的字段同名，跨项目零翻译成本。
- **主方向是「个/元」**（`price` / `unit`、以及挂单的 `pricePerYuan` 都是这个方向）。元价只到 4 位小数、比率价到 3 位以上且是接口原始值（[ADR-0006](./0006-api-response-as-price-source.md) 结论 2）。
- **挂单存 3 个字段**：`{ stock, pricePerYuan, ratioUnit }`。挂单行的元方向**由 `stock ÷ pricePerYuan` 得出**，不另存——`pricePerYuan` 是接口原始值，显示与总价同源，用户拿屏幕上的两个数即可验算。
- 渲染时两个方向并列显示——**不做任何换算**；主方向在前，元方向在括号里（`8.417 个/元 (0.1188 元/个)`）。
- 读不到的那一行省略，不影响另一行。
- 抓取端有**形态守卫**与一条**响亮失败**（卡片读到了但一张都读不出价格 = 选择器过期），因为"两行都没读到"与"这个通货没有挂单"在结果上长得一样。

⚠️ **这条推翻了本 ADR 初稿的结论**。初稿写的是"取第二个方向、需要另一个方向时读那一行"。那个结论的前提（两行互逆）是错的，且已经在实现中产出过错值。

⚠️ **"两个方向是两个独立的事实"这条纪律在实现中又被违反过一次。** 抓取源项目的 DOM 兜底路径曾对挂单卡的价格行取过一次倒数，而那一行（`1 元 = 8.4746 个`）**本身就是比率价**——结果是**同一份产物里同一个字段名两个方向**：走接口的通货写 `52.6537`、走 DOM 兜底的写 `0.118`（其实是 `8.4746` 的倒数），**两者单看都像正常价格**。它只在与同区服市价对照时才暴露：`0.118` 意味着每个 8.47 元，而该区服市价是 `0.1267 元/个`——**差 67 倍**。所以方向不能只写在注释里，要在**纯函数层用测试钉死**。

**3. 详情逐通货开启、默认关闭**。取详情要为每个通货多做一次页面交互，抓取时长与失败面都随之变大，应当由用户显式付这个代价。

**4. 详情开关进配置指纹**。`currencyList` 每条含 `detail` 开关，因此开关本身就在指纹里——开启后旧数据（那份里没有详情）立即判过期，不需要等 5 分钟的新鲜度窗口。

**5. 详情失败不判游戏失败**，只记 `null`，价格照常落盘。**唯一能改写价格的是它的挂单深度**——深度不足以构成市价时该条价格判为失真、记 `null`，见 [ADR-0007](./0007-thin-market-means-distorted.md)。因此「`price` 为 `null`、`detail` 里却有挂单」在本项目里是**合法组合**。

**6. 详情块的三种状态不可归一**：**没开详情**（字段不存在）、**开了但没取到**（`null`）、**取到了**（对象）。归一会让"为什么这份数据没有详情"变成无法回答的问题。

## 后果

**代价（已知且接受）**：

- **消息变长**。每个开了详情的通货会多出一行成交量加 N 行挂单，而定时推送是每小时一次。行数偏多时的收紧方式是改渲染（比如只显示最低价那条），而不是改数据形状——抓取端的成本已经付过了。
- **抓取时长上升**。每个通货多一次点击与一次面板等待。实测详情单条在数百毫秒到 3 秒之间，全量开启会让单轮抓取显著变长。
- ~~**交叉比对的容差被迫放宽**~~（**已作废**）。这一条依赖「DOM 与接口交叉比对」是价格的正确性防线，而 [ADR-0006](./0006-api-response-as-price-source.md) 结论 6 已把该防线**删除**：价格改由接口定，比对降级成"等不等 DOM"的判据，判错不再写进错值。
- **数据体积约翻倍**。价格与挂单都存两份方向，30 天归档按日切分后再 gzip，可接受。
- **盘口数据的展示与分析边界从此靠纪律维持**，不再有文档层面的阻挡。

**已记录的观察项**：原为「容差 10% 偏松」，已随 [ADR-0006](./0006-api-response-as-price-source.md) 删除交叉比对而作废。**新增一条**：**DOM 兜底路径会很少被执行**——它是"站点接口改版时的降级通道"，主路径根本不走它。这类代码会腐烂，因此必须留在纯函数层并保住单测，否则真到要用时它已经坏了。

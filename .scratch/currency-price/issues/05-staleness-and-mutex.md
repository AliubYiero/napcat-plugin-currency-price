# 05 — 数据新鲜度与互斥排队

Status: ready-for-human
Type: AFK
Blocked by: 04
来源: [docs/design.md](../../../docs/design.md) §4 §9.2 §9.3 §9.4 §12.2 §12.3

## What to build

端到端行为是：A 游戏 2 分钟前刚抓过、B 游戏 15 分钟前抓过，用户发 `#currency price`，机器人**只重抓 B**，然后展示 A 和 B——A 用的是现成数据，用户看不出区别，但抓取确实没跑第二遍。

另一个端到端行为：两个人几乎同时发 `#currency price`，后者排队等待，轮到自己时**重新计算**需要抓的游戏（前者可能已经抓过了，此时直接复用）。

要落定：

**新鲜度判定按游戏逐个做** —— `now - game.readAt > 5 分钟`（或该游戏从未抓到、`readAt` 不存在）→ 过期，需要抓；否则复用。判定依据是**该游戏自己的 `readAt`**——不是全局时间戳，也不是「用户能不能发指令」。

**阈值 5 分钟是常量**（`STALENESS_THRESHOLD_MS`），**不是配置项**——它与「用户会不会想改」无关，属于领域语义。

**全局一把锁，后到者排队** —— 不是「复用前者结果」：在游戏级粒度下前者可能根本没抓你要的游戏。后到者轮到自己时**重新计算**需要抓的游戏。

**代价要说清并且接受**：先触发者先收到自己的结果，后到者在锁释放后再抓自己缺的游戏、再推给自己——**两人可能收到内容不同的两条消息**。这是设计决策，不是 bug。

**不做游戏级并发** —— 现有抓取是多个游戏共用同一个 page 串行（UA 挂在 context 上，页面状态在组合间累积），并发就得开多个 browser/page。而「两个会话同一分钟都发 price」是低频事件，排队等一两分钟是可接受的代价。单次抓取持有 **1 个浏览器 + 1 个 context + 1 个 page**，抓完即关。

**这只锁调度层与手动抓取共用**（调度层在片 08 接入，本片先把锁与「抢锁后重算」的结构做对）。

## Acceptance criteria

- [x] A 游戏 2 分钟前抓过、B 游戏 15 分钟前抓过时，`#currency price` **只重抓 B**，然后展示 A 和 B
- [x] 全部订阅游戏都新鲜时，`price` 完全不启动浏览器，直接展示
- [x] 从未成功抓到过的游戏（`readAt` 不存在）判为过期
- [x] 展示用 `data.json` 渲染，头部时间用**游戏级** `readAt`，转本地时区
- [x] 两个会话几乎同时 `price`：后者排队等待，且**轮到自己时重新计算**过期集合（前者已抓过的游戏不重复抓）
- [x] 排队期间先触发者先收到自己的结果；后到者的结果在锁释放后发出（接受两人收到内容可能不同的两条消息）
- [x] 手动抓取先回执「正在抓取…」
- [x] 单测覆盖：过期判定（边界恰好 5 分钟）、从未抓取、全部新鲜、部分过期
- [x] 抓取期间同时存在的 page 数始终为 1

## 实现期判断

- **本片实际随片 08 一并落定**（它是 08 触发序列的硬前置）：模块为 `services/staleness.ts`（`STALENESS_THRESHOLD_MS = 5 * 60 * 1000` 常量, 非配置项; `isStaleGame` 边界严格大于）与 `services/scrape-lock.ts`（`runWithScrapeLock`, 全局 FIFO 队列, 单个任务的失败只属于调用方不传染）。
- `price.handler` 已按 §12.2 改造：全部新鲜 → 不回执不抓直接展示；有过期 → 回执 → 抢锁 → **轮到自己时重算** → 共享 `runScrapeRound` 抓过期的并归档（`manual:{会话键}`）→ 展示全部订阅。
- 「先触发者先收到」由结构保证（排队者不阻塞先行者的回复路径），未做端到端双会话消息顺序断言——锁的单测覆盖了串行与重算语义。

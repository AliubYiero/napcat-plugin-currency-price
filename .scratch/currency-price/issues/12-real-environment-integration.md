# 12 — 真实环境联调验收

## What to build

把前面所有切片在**真实 NapCat 部署环境**里连通一遍——不是单机跑通，是「加载 → 装浏览器 → 抓取 → 定时推送 → 指令 → WebUI」全流程在部署机上跑通。

**这一片需要人**：验收判据是用户在人真在的群里看到的推送内容，机器人是否按时送达，安装 Chrome 是否真的装上——这些无法由 agent 自己断言。

**为什么单列一片而不是散在各片**：第 0 步已经暴露过，本项目的失败模式集中在「构建通过、运行时才炸」，而单机跑不出的问题（Linux 无浏览器、真实 QQ 频控、真实站点 UA 拦截）只能在这一片暴露。散在各片会让每片都以为自己验完了。

**已知要用的手法** —— 远程可观测性只有 `runtimeError` 一个通道：调试服务**没有**读远程日志 / 读远程文件的 RPC，`plugin_init` 的任何输出都传不回来。第 0 步是靠「跑完后临时抛异常」把遥测塞进 `runtimeError` 才取到的。本片会再需要它。**这条要写进验收记录，因为它是一个会反复需要重新发现的技巧。**

**必须覆盖的验证场景**：

- 加载与卸载：`runtimeStatus: "loaded"`；卸载后浏览器被正确关闭；热重载后不残留定时器
- 浏览器获取：在**本来没有浏览器**的部署机上走完「状态卡显示不可用 → 点安装 → 装上 → 状态可用 → 抓取能跑」
- 抓取：真实站点抓取成功；人为断网 / 改错 URL 触发失败路径，确认旧值与「（数据未更新）」标记
- 定时推送：在配置的整点真实收到推送；确认未选中的小时没有推送；确认推送包含因新鲜而跳过的游戏且**无**标记
- 指令：在群里与人一起验证三类失败文案、权限档位（含超管在别人的群里执行admin 指令）、帮助图片
- WebUI：改 `catalogs` 后无需重启即生效；**开着面板放几分钟**，确认没有反复拉起浏览器
- 归档：次日 gzip 真实发生
- 频控：`pushIntervalMs` 默认 `100` 在真实 QQ 服务端**是否够用**——不够就调大并回写设计文档

## Acceptance criteria

- [ ] 设计文档 §20.1「功能」清单**全项**通过
- [ ] 设计文档 §20.2「非功能」清单**全项**通过
- [ ] 在远程 Linux 部署机上走完完整链路：加载 → 安装浏览器 → 抓取 → 定时推送 → 指令 → WebUI
- [ ] 定时推送在真实 QQ 会话里被用户真实收到并确认内容正确
- [ ] `#currency price` 的抓取耗时在真实环境下记录（全部成功路径）
- [ ] `pushIntervalMs` 在真实 QQ 服务端下验证过；若需调整，已回写设计文档 §5.1 与 §21
- [ ] 卸载 / 重载后无残留定时器，浏览器被关闭
- [ ] 联调中发现的任何与设计文档不符之处，**回写设计文档**而不是默默按代码走（设计文档是设计意图的长期权威）
